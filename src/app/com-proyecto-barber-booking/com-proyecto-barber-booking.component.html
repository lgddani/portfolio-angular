Barber Booking System

Un sistema de reservas full-stack para una barbería: tres roles con permisos reales, un motor de disponibilidad que entiende la duración de cada servicio, y una garantía a nivel de base de datos de que dos clientes nunca reservan el mismo horario con el mismo barbero — incluso bajo concurrencia real.

46 tests de backend en verde
15 hilos reales peleando por un horario
3 roles con permisos propios
2 imágenes Docker en dos etapas

No es solo agendar una hora

Barber Booking System gestiona las citas de una barbería, pero el reto no es la agenda en sí: es evitar que dos personas reserven el mismo horario con el mismo barbero, calcular qué horarios están realmente disponibles tomando en cuenta el horario de trabajo de cada barbero, sus días libres y cuánto dura cada servicio, y asegurar que cliente, barbero y administrador solo puedan hacer lo que les corresponde. Es un proyecto de portafolio — ninguna barbería real lo usa —, pero está construido con el mismo cuidado que tendría un producto real.

¿Por qué no hay una demo en vivo?

Los planes gratuitos de hosting para backend "duermen" la API tras un rato sin uso: el primer clic de alguien revisando esto se habría encontrado con 30-50 segundos de carga fría antes de ver algo, peor primera impresión que no tener demo. Tres roles, tres pantallas distintas

No es una sola pantalla con permisos maquillados detrás: cada rol tiene su propia interfaz, construida para lo que ese rol necesita hacer.

Desafío técnico — que dos personas no se lleven el mismo horario

La solución obvia es un bloqueo a nivel de aplicación, o un SELECT ... FOR UPDATE de verificar-y-luego-insertar. Ambas funcionan — hasta que hay más de una instancia del backend corriendo, momento en el que la garantía deja de sostenerse en silencio. La decisión fue trasladar esa regla al único lugar que es autoritativo sin importar cuántas instancias existan: la propia base de datos.

CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE appointments
  ADD CONSTRAINT no_overlap_per_barber
  EXCLUDE USING gist (barber_id WITH =, slot WITH &&)
  WHERE (status NOT IN ('CANCELLED', 'NO_SHOW'));

ALTER TABLE appointments
  ADD CONSTRAINT no_overlap_per_customer
  EXCLUDE USING gist (customer_id WITH =, slot WITH &&)
  WHERE (status NOT IN ('CANCELLED', 'NO_SHOW'));

Si dos peticiones intentan reservar al mismo barbero en un horario que se solapa, PostgreSQL deja pasar exactamente un INSERT y rechaza el otro con una violación de restricción — de forma atómica, sin ningún bloqueo explícito escrito a mano.

El hallazgo más interesante del proyecto

Con 12 peticiones concurrentes de prueba manual, solo aparecía el modo de falla "limpio" (una violación de restricción). Al automatizar la prueba con 15 hilos reales apareció una segunda variante: bajo suficiente presión, Postgres a veces detecta que varias transacciones se esperan entre sí en círculo y cancela una con deadlock detected en vez de la violación esperada.

Para quien está reservando, ambos casos significan exactamente lo mismo —alguien más se quedó con ese horario—, así que el código traduce las dos variantes al mismo 409 Conflict. La lección: probar con pocos casos concurrentes (2-3) puede no ser suficiente para encontrar todos los modos de falla reales; algunos solo aparecen bajo carga de verdad.

Desafío técnico — calcular qué horarios están realmente libres

Esto no es una sola consulta. Hay que combinar la plantilla semanal recurrente del barbero con las excepciones de esa fecha puntual —un día cerrado, o un horario especial que reemplaza al habitual, no que se le suma—, considerar la duración exacta del servicio pedido, descartar lo que ya está ocupado, y descartar lo que ya pasó si es el mismo día.

Al ser una función pura (mismos datos de entrada, mismo resultado, sin efectos secundarios) terminó siendo la pieza con más cobertura de tests unitarios del proyecto: casos límite como un servicio que por poco no alcanza a caber antes del cierre, o una excepción de horario completamente distinto al habitual, se prueban de forma directa.

Del mockup al resultado

Antes de escribir una sola línea de Angular, se armaron y compararon dos opciones de estilo visual con una herramienta de mockups: una cálida, propia de una barbería real, y otra minimalista tipo SaaS genérico. Ganó la cálida — encajaba mejor con lo que el sistema realmente es.

Más adelante, para el panel de administrador, partí de una referencia visual de un dashboard más profesional. Antes de tocar código se conversó el alcance —qué tan real hacer la campana de notificaciones, si rediseñar todas las pantallas de una vez o empezar por una— para no comprometerme a más trabajo del necesario en esa pasada. El resultado: Servicios, Barberos y Citas pasaron de tarjetas fijas a tablas de verdad con buscador, paginador y un formulario en modal centrado. Estadísticas no encajaba en ese mismo patrón —no es una lista de cosas que administrar, son números resumidos— así que se le dio su propio tratamiento: tarjetas con ícono y barras proporcionales por estado.

Una decisión de criterio, no de un bug

No todo en este proyecto fue arreglar algo roto — a veces fue elegir bien entre opciones que sí funcionaban. Para el frontend se probó primero spartan/ui, pero todas sus versiones publicadas piden una versión de Angular más nueva que la que usa este proyecto: se descartó sin forzar una combinación que nunca iba a sostenerse. La segunda opción, PrimeNG, sí calzaba en versión —compiló bien— pero esa versión específica requería una licencia paga, un modelo de negocio legítimo que no encaja con un portafolio que cualquiera debería poder clonar y correr gratis. Terminé optando por Angular Material: la librería oficial del propio equipo de Angular, siempre gratuita y alineada en versión el mismo día que sale cada release.

Reproducible por cualquiera, no solo en mi máquina

Base de datos, backend y frontend se levantan juntos con un solo comando: docker compose up --build. Ambos servicios usan Dockerfiles de dos etapas —una que compila (Maven o npm), y otra, mucho más liviana, que solo carga el resultado ya compilado para ejecutarlo— así la imagen final no arrastra las herramientas de build. nginx sirve el frontend ya compilado y de paso hace de puente hacia el backend dentro de la red privada de Docker, sin que el navegador necesite saber que en realidad son dos servidores distintos.

Cada push dispara GitHub Actions: el backend corre sus 46 tests completos levantando su propio Postgres real vía Testcontainers —igual que en cualquier máquina—, y el frontend compila la aplicación Angular. Así, si algo se rompe, se sabe de inmediato sin que nadie tenga que acordarse de correrlo a mano.
